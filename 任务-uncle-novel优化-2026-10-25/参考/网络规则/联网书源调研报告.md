## 2. 调研与验证方法

应用启动时 `RuleManager` 静态初始化调用 `RuleHelper.loadRules(conf\rules.json 内容)`，规则列表由 `RuleHelper.rules()` 提供；「全网搜书」只使用 `enabled=true && isEffective() && audio!=true && search.isEffective()` 的规则。因此本报告用**三层验证**，全部直接调用应用自带 jar：

1. **能否被 app 加载** —— `TestRules.java`：`RuleHelper.loadRules(json)` → 打印 `loadRules` 返回值、`rules().size()`、每条 `isEffective()` / `search.isEffective()`。
2. **能否搜出书** —— `SearchTest.java`：调用 `NovelMatcher.search(1, keyword, rule, callback)`，走真实 HTTP + 规则解析（XPath/CSS/JSONPath/JS 脚本），输出每条规则命中书籍数与耗时。
3. **能否解析下载** —— `DownloadTest.java`：`NovelSpider.details()/toc()/content()`，验证「详情→目录→正文」整条下载链。
4. 辅助 **Python 原始 HTTP 探针**：记录状态码、重定向、编码、反爬特征、列表 XPath 命中数（`lxml` 近似，仅作参考，最终以 Java 端结果为准）。

验证脚本位于 `任务-uncle-novel优化-2026-10-25\工具\net-rules\`（`TestRules.java`、`SearchTest.java`、`DownloadTest.java`、`InspectRule.java`、`probe_sites.py` 等），复测命令见 §7。

> 关键点：社区规则里写的是「规则」，但站点是否活着、HTML 是否改版，只能实测。**规则能解析 ≠ 能搜出书 ≠ 能下载**，本报告逐层区分。

### 5.1 红袖规则修复（API 型，脚本改动）

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| `search.detail.url` 的 `replace` 未生效 | 目录请求 404：`https://appapi.hongxiu.com/api/v3/search/<bookId>` | 改为 `script` 拼接：`"https://appapi.hongxiu.com/api/v1/chapter/list?bookId=" + result + "&lastChapterId=0&md5Signature= h2"` |
| 正文换行异常 | 正文里是**字面量** `\r\n`（JSON 未反转义），阅读器会显示「\r\n」字样 | 改为脚本清洗：`new java.lang.String(result).replaceAll(java.util.regex.Pattern.quote("\\r\\n"), "\n")` |

> 说明：JSONPath（`$`）取值得到的文本里，`CommonRule.replace`（`正则##替换`）实测未按预期生效——正文两轮验证中 75 处字面量 `\r\n` 全部保留；同一位置改用 `script` 清洗后 75 处全部转换成功。原规则的 `search.detail.url` 的 `replace` 拼接同样未生效（落到错误 URL 404）。这是本机 analyzer 版本的行为差异，用户自建规则时建议优先用 `script` 处理 JSON 字符串的转义换行与 URL 改写。

### 5.2 书趣阁规则重建（域名迁移 `shuquge.com` → `xshuquge.net`）

- 原规则：`POST https://www.shuquge.com/search.php`，body `searchkey={{keyword}}` → 现在会 301 到 `xshuquge.net`，返回**空结果页**（关键词被丢弃）。
- 新规则（本次重建，已实测）：
  - 搜索：`POST http://www.xshuquge.net/search.php`，body `s=&searchkey={{keyword}}`（**必须 http**，https 返回 404）
  - 列表：`css:div.bookbox`；书名/作者/分类/最新章均用相对 CSS
  - 目录：`css:div.listmain > dl > dd`（约 1900+ 章）
  - 正文：`//div[@id="content"]/text()`（自动带正常段落换行）

### 5.3 365小说网规则修复（社区 2025 规则优化）

原规则两处问题：
1. `search.detail` 里有 `"page": "detail"` 字段（封面/字数/更新时间），analyzer 会为**每条搜索结果各抓一次详情页**：48 条结果 ≈ 55 秒，体验差；
2. 部分书详情页 URL 是 `/book/<id>/`（书信息页，**没有章节目录**），导致 `toc()` 返回 0 章（如「斗破苍穹」第一次实测）。

修复后：
- `search.detail` 全部改相对 CSS（`css:div.bookdesc > a@href` / `h2@text` / `p.sp > span:nth-child(1)@text` 等），搜索只发 **1 个请求**：50 条 / 1.6~2.3 秒；
- 书 URL 用 `script` 自动补 `/index.html`（`/book/18756/` → `/book/18756/index.html`），目录 1914 章、正文正常；
- 规则中的「详情页字段」保留在顶层 `detail`（打开书籍时按详情页解析，不影响列表速度）。

### 5.4 番茄小说（仅搜索；目录/正文接口已失效）

- 搜索可用：`https://novel.snssdk.com/api/novel/channel/homepage/search/search/v1/?aid=13&q={{keyword}}`，10 条结果、含书名/作者/分类/简介/封面，0.4~0.8 秒；
- 目录 API `https://api5-normal-lf.fqnovel.com/reading/bookapi/directory/all_items/v/...`：HTTP 200 但 **body 长度 0**；备选端点（`multi-detail`、`api5-normal-sinfonlineb`、`novel.snssdk.com/.../directory/detail`）同样返回空/`invalid client`，需要客户端签名（`X-Argus` 等），非规则可修复范围；
- 结论：番茄规则**只保留「搜书」能力**，点击下载会失败；`rules-可用.json` 中 weight 设为 99（排最后），建议默认不内置（由 Lead 决定）。

- app 按段落逐段合成（每段失败会 toast「音频获取失败」），本测试文本长度与章节段落相当，未触发长度限制；
- 思必驰接口稳定但延迟略高（1.1~1.4s/段），朗读翻页时 app 有预缓存（`TTSPlayer` 缓存任务），实际体验可接受。

## 8. 风险与限制

1. **反爬/风控**：Cloudflare 人机验证（西红柿 403）、连接重置（燃文）会直接让规则失效；后续新源需注意 UA/Cookie/Referer。
2. **域名迁移与关停**：本次 16 个站点中 12 个失效，其中 6 个域名已不存在。社区书源 2022 年后基本停更，**书源是有保质期的**；书趣阁这类「老域名跳新域名」的情况会越来越常见。
3. **API 型规则易失效**：番茄目录 API 已返回空 body；红袖部分接口依赖 `deviceinfo` 头（规则里已内置，但服务端随时可能升级签名）。
4. **dynamic/JS 渲染规则不可用**：规则 `params.dynamic=true` 时 analyzer 会尝试启动浏览器（本机无 PhantomJS/Chromium 驱动），且本机应用路径含空格，实测报 `Cannot run program "...\v"`。这类规则（如笔趣阁）应视为不可用。
5. **编码**：GBK 站点必须在 `search.params.charset` 写 `GBK`（如原笔趣阁规则）；UTF-8 站点留空即可。正文编码错会乱码。
6. **请求量与站点压力**：原 365 规则一次搜索发 49 个请求（列表 + 48 详情页），既慢又容易被封；已优化为 1 个请求。自建规则时避免 `page:"detail"` 字段滥用。
7. **版权与合规**：这些站点均为转载/聚合站，随时关停；书源仅供个人学习研究使用，请勿传播或商用。
8. **规则安全性**：规则里的 `script` 会由应用执行（Nashorn JS），可调用 Java 类；**只导入可信来源的规则**。
9. **规则顺序**：`RuleHelper` 内部按 site 映射存储，JSON 文件顺序 ≠ 搜索顺序；优先级请用 `weight`。
