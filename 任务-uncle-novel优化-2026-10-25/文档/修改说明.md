### 1.2 启动链（实测 + 日志/字节码核实）

```text
Uncle小说.exe（exe4j，embeds uncle-novel.jar）
   └─ com.unclezs.jfx.launcher.Launcher     ← jfx-launcher 1.1.11-SNAPSHOT（uncle-novel.jar，28,629 B）
        ├─ 读取本地 manifest：conf\app.json
        ├─ 联网检查更新：<app.json.url> + /conf/app.json
        │    成功且无新版 → newVersion=false
        │    检查失败/异常 → 捕获异常 → newVersion 保持构造器默认值 true
        ├─ 构造 Stage 并 stage.setUserData(Map.of("changeLog",…, "version",…, "hasNew", newVersion))
        └─ Application.start(stage) → com.unclezs.novel.app.main.App
             └─ App.start(): stage.show(); UpdateUtils.checkForUpdate(stage)
                   → 读取 stage.getUserData() 的 hasNew；为 true 时弹出「当前版本 - VX.Y.Z」更新日志对话框
```

**关键点（决定了本优化的方案选择）：**

1. 启动器 `Launcher` 的 `newVersion` 字段在构造器中默认置 `true`（字节码 `iconst_1; putfield newVersion`）。
2. 更新检查 `syncManifest()` 的异常表覆盖了“加载远程 manifest / 判断新版本”整段；DNS 失败时进入 catch，仅记录 `严重: 更新失败` 并 `return false`，**`newVersion` 不会被置为 false**。
3. 启动器随后把 `hasNew = newVersion (=true)` 通过 `stage.setUserData(...)` 传给应用；应用 `UpdateUtils.checkForUpdate` 据此弹更新日志。
4. 因此，只要网络环境无法访问更新服务器，**原版每次启动都会弹更新日志**——与用户设置、版本新旧无关。
5. JVM 参数唯一官方入口 = `conf\launcher.vmoptions`（exe4j 的 `-include-options` 引入；实测 `jcmd VM.flags` 生效）。

### CHG-01 应用层移除「每次启动的更新日志弹窗」（`app.jar` 字节码补丁）

#### 3.1.1 定位

| 项 | 值 |
| --- | --- |
| 目标 jar | `runtime\modules\app.jar` |
| 目标条目 | `com/unclezs/novel/app/main/App.class`（class 文件长度 **7,434 B**，未变化） |
| 目标方法 | `public void start(javafx.stage.Stage) throws java.lang.Exception` |

#### 3.1.2 修改方法

1. 用 zip 工具解包 `app.jar`（保留 `META-INF\`、`module-info.class`、资源目录）。
2. 取出 `com/unclezs/novel/app/main/App.class`，确认偏移 6498 处 4 字节为 `2B B8 00 1D`（全局仅出现 1 次，若不符立即中止）。
3. 将 4 字节等长替换为 `00 00 00 00`。
4. 重新打包为 `app.jar`，覆盖 `runtime\modules\app.jar`。
5. 用 `javap` 复验（见 §3.1.3），并用 `Get-FileHash` 与 §2 的 SHA256 对比。

复现脚本示例（Python 3，任选其一；本仓库的 `参考\app-patched.jar` 即结果）：

```python
import io, zipfile

BASE = "C:/path/to/uncle-novel"          # 安装目录
src_jar = BASE + "/runtime/modules/app.jar"
buf = io.BytesIO()
with zipfile.ZipFile(src_jar) as zin, zipfile.ZipFile(buf, "w", zipfile.ZIP_DEFLATED) as zout:
    for item in zin.infolist():
        data = zin.read(item.filename)
        if item.filename == "com/unclezs/novel/app/main/App.class":
            assert data[6498:6502] == bytes.fromhex("2BB8001D"), "补丁特征不匹配，已中止"
            data = data[:6498] + bytes.fromhex("00000000") + data[6502:]
        zout.writestr(item, data)
open(src_jar, "wb").write(buf.getvalue())   # 覆盖前请先备份为 app.jar.orig
```

> 审计注记：本仓库的 `参考\app-patched.jar` 与官方 `app.jar.orig` 逐条目比对结果——共 250 → 195 个条目，减少的 55 个全部是空的目录条目（`META-INF/`、`com/...` 等）；**文件条目内容除 `App.class` 外全部一致（长度、CRC 相同）**；`App.class` 长度不变（7,434 B），仅上述 3 个字节变化。目录条目缺失不影响 JAR 运行，实测多次启动正常。若需严格保持原条目结构，复现脚本按 `infolist()` 原样写回即可（本补丁不依赖该差异）。

#### 3.1.4 风险、副作用与回退

- **已验证的风险点**：class 文件版本与结构未变（仅 1 条指令被等长 NOP 覆盖，Code 属性长度、行号表、StackMapTable 不受影响），JVM 校验通过。
- **副作用**：`UpdateUtils.checkForUpdate` 里除弹窗外还会执行 `SettingManager.manager().setVersion(version)`（把启动器传来的版本号写入设置）以及读取 `stage.getUserData()`。补丁后这一调用整体跳过，因此**不再由启动器刷新设置中的版本字段**；版本显示仍来自 `conf\app.json`（5.0.44），实测主界面/设置/阅读等功能均无影响。
- **未受影响**：`MixPanelHelper.event("启动应用")` 与启动耗时日志仍照常执行（补丁只覆盖 4 字节）。
- **回退**：用 `参考\app.jar.orig` 覆盖回 `runtime\modules\app.jar`，重启应用即恢复原行为（会重新弹更新日志）。

### CHG-02 更新检查改为本地快速失败（`conf\app.json`）

#### 3.2.1 变更内容

`conf\app.json` 是启动器的本地 manifest（单行 JSON，含 `url`、`version`、`changeLog`、`resources`、`launchClass`、`moduleOptions` 等）。**仅修改 `url` 一个字段**，其余内容与官方逐字节一致（已用「替换后字符串全等」比对确认）。

| 字段 | 原始值 | 新值 |
| --- | --- | --- |
| `url` | `https://update-uncle-novel.unclezs.com/novel/prod/` | `http://127.0.0.1:1/` |

修改后启动器实际请求的远程 manifest 地址由日志确认：

- 原版：`获取远程配置文件:https://update-uncle-novel.unclezs.com/novel/prod/conf/app.json` → `UnknownHostException`（等待 DNS 超时/失败）
- 优化版：`获取远程配置文件:http://127.0.0.1:1/conf/app.json` → `ConnectException: Connection refused: connect`（本机端口 1 无监听，立即失败）

#### 3.2.2 修改方法与验证

- 修改：编辑 `conf\app.json` 的 `url` 字段并保存（UTF-8，保持单行 JSON；改完用 `ConvertFrom-Json` 校验合法性）。
- 验证：启动后查 `logs\log-system.log`，应出现上述 `127.0.0.1:1` 请求 + `更新失败` + `正在初始化运行环境... / 正在启动应用...`；应用正常进入主界面。另用 `Resolve-DnsName` 确认三个域名（`uncle-novel.unclezs.com` / `update-uncle-novel.unclezs.com` / `app.unclezs.com`）均无法解析。

#### 3.2.3 风险与回退

- **风险**：极低。地址与证书/域名无关，仅本机回环地址；即使本机恰好有服务监听 1 端口（几乎不可能，且需特权），最坏结果也只是更新检查得到异常数据 → 仍走“失败继续启动”路径。
- **稳定性**：启动器仅在**成功获取远程 manifest 且判定有新版本**时才会回写本地 `app.json`；当前地址永远失败，因此该改动不会被自动覆盖。
- **日志副作用**：每次启动 `logs\log-system.log` 会记录一条 `严重: 更新失败`（预期行为，不是故障）。
- **回退**：用 `参考\app.json.orig` 覆盖回 `conf\app.json`（恢复原域名，启动会重新等待 DNS 失败/超时）。

### CHG-03 JVM 参数调优（`conf\launcher.vmoptions`）

#### 3.3.1 变更内容

官方出厂文件只有 1 行（32 字节）；优化后 6 行（137 字节，UTF-8、LF）：

```diff
 -Djava.net.useSystemProxies=true
+-Xms128m
+-Xmx1024m
+-XX:MaxMetaspaceSize=256m
+-XX:ReservedCodeCacheSize=128m
+-Dprism.lcdtext=false
```

| 参数 | 作用 | 选择理由 / 实测 |
| --- | --- | --- |
| `-Djava.net.useSystemProxies=true` | 沿用官方：使用系统代理设置 | 官方默认，保留 |
| `-Xms128m` | 初始堆 128 MB | 应用常驻堆实际使用很低（Used 约 40–55 MB），小初始堆避免一上来就占大内存 |
| `-Xmx1024m` | 最大堆 1 GB | 给极端场景（大文件解析/批量下载）留余量，同时限制最坏膨胀 |
| `-XX:MaxMetaspaceSize=256m` | 元空间上限 | 防元空间无上限增长；正常使用远低于此值 |
| `-XX:ReservedCodeCacheSize=128m` | JIT 代码缓存上限 | 防代码缓存膨胀；JavaFX 应用常用区间内 |
| `-Dprism.lcdtext=false` | 关闭 Prism 的 LCD 次像素文字渲染 | 中文界面文字边缘不再出现彩色镶边（截图人工目检），观感更干净；对性能影响可忽略 |

#### 3.3.2 修改方法与验证

- 修改：直接编辑 `conf\launcher.vmoptions`（每行一个参数，无 BOM）。这是 exe4j `vmParameters="-include-options ..."` 引入的**唯一官方参数入口**，改 exe/其他位置无效。
- 验证（应用运行时执行，使用自带 `runtime\bin\jcmd.exe`）：
  - `jcmd <java_pid> VM.flags` → 实测 `MaxHeapSize=1073741824`（=1 GB）、`MaxMetaspaceSize=268435456`（=256 MB）、`ReservedCodeCacheSize=134217728`（=128 MB），并可见 `-Xms128m` 等；
  - `jcmd <java_pid> VM.system_properties` → 实测含 `prism.lcdtext=false`、`java.net.useSystemProxies=true`；
  - 应用启动、主界面、阅读均正常。

> 内存说明：实测 RSS 约 700–740 MB，堆 committed 约 378–415 MB、Used 约 40–55 MB；G1 与 SerialGC 对比未观察到量级差异。**内存参数的价值是“上限约束/可预测”，不是降低 RSS 或明显提速**，文档与对比报告均不夸大。

#### 3.3.3 风险与回退

- **风险**：参数均为 `-XX` 软上限类，写错只影响启动（Java 启动时对未知参数会告警/报错）。**不要随意改 `-Xmx` 超过物理内存 1/2**。
- 回退：用 `参考\launcher.vmoptions.orig` 覆盖回 `conf\launcher.vmoptions`（恢复单行官方配置）。

### CHG-04 体积裁剪：删除非 Windows 的 kindlegen

#### 3.4.1 变更内容

| 文件（相对安装目录） | 大小 | 用途 | 处置 |
| --- | --- | --- | --- |
| `bin\kindlegen` | 23,163,488 B | macOS 版电子书转换组件 | **删除** |
| `bin\kindlegen_linux` | 28,752,467 B | Linux 版电子书转换组件 | **删除** |
| `bin\kindlegen.exe` | 7,908,160 B | Windows 版电子书转换组件（MOBI 导出用） | **保留** |

依据：`conf\app.json` 的 `resources` 清单中，三者分别标注 `platform: MAC / LINUX / WIN`；Windows 运行时只会调用 `kindlegen.exe`。

#### 3.4.2 修改方法与验证

- 修改：删除两个文件（无需改 `app.json` 的资源清单）。
- 为什么可以不改清单：启动器的 `checkForUpgrade()` 只在 `syncManifest()` 判定“有新版本”时才执行 `syncResources()`（资源校验/补全）；当前更新地址永远失败 → `syncManifest` 返回 false → **资源校验流程不会触发**，清单中的条目不会被检查，也不会触发下载。实测多次启动正常。
- 验证：删除后目录体积 153,715,684 B（146.6 MiB），相对原版 205,638,760 B（196.1 MiB）减少 51,923,076 B（约 49.5 MiB / -25.6%）；应用启动、主界面正常；未实测 MOBI 导出（Windows 组件保留，理论不受影响）。

#### 3.4.3 风险与回退

- **风险**：如果未来改用 Mac/Linux 版，需要这两个文件（本优化只针对 Windows 安装目录，不涉及跨平台包）。
- **未做**：没有同步删改 `app.json` 的 `resources` 清单（保持“只改必要字段”原则，减少启动器配置被改坏的风险）。
- 回退：从 `1-原版\uncle-novel\bin\` 或官方 zip 中把 `kindlegen`、`kindlegen_linux` 拷回 `bin\`。

### CHG-05 安装位置与快捷方式（部署层）

#### 3.5.1 变更内容

| 项 | 官方默认 | 本优化版 |
| --- | --- | --- |
| 安装位置 | `Setup.exe` 默认 `{autopf}\Uncle小说`（Program Files，需管理员/易含中文） | `%LOCALAPPDATA%\Programs\UncleNovel`（纯 ASCII、当前用户可写、无需 UAC） |
| 启动方式 | 无快捷方式或由 Inno Setup 创建 | 桌面 + 开始菜单 `Uncle小说.lnk`，**目标 = `<安装目录>\Uncle小说.exe`，起始位置 = 安装目录**，图标 = `<安装目录>\favicon.ico` |
| 数据目录 | = 进程当前工作目录（取决于启动方式，可能跑到 System32 等目录） | 同上，但快捷方式固定起始位置，数据稳定落在安装目录 |
| 单实例 | exe4j `singleInstance="true"` | 不变（重复双击只唤起已有实例） |

#### 3.5.2 字体问题根因与验证（为什么必须 ASCII 路径）

原版日志（`1-原版\uncle-novel\logs\log-error.log`）在每次启动时重复出现：

```text
10:31:49.857 [FX] ERROR c.u.novel.app.framework.support.fonts.FontsLoader - 加载pingfang-simple-bold.ttf字体失败
...（同一行共 16 条，10:31–10:56 多次启动记录；每次启动记录约 120 字节）
```

源码逻辑（`app-framework\...\support\fonts\FontsLoader.java`）：遍历 `fonts\` 目录，把文件转成 URL 后调用 `Font.loadFont(url, size)`；返回 `null` 即打印“加载…字体失败”。

定位结论（实测）：

1. 字体文件本身有效：`fonts\pingfang-simple-bold.ttf`（10,646,300 字节）文件头为 `OTTO`（OpenType），不是损坏文件。
2. 在**纯 ASCII 路径**（如 `C:\Temp`）下用 JavaFX 的 `Font.loadFont` 加载该文件，返回字体族 `.PingFang SC` —— 加载成功。
3. 同一文件放在**含中文字符的路径**（本工程所在 `...\任务-uncle-novel优化-2026-10-25\1-原版\uncle-novel\fonts\...`）下，`Font.loadFont` 返回 `NULL` —— 加载失败。
4. 结论：**根因是安装路径含中文，不是字体文件损坏**；改用纯 ASCII 安装路径后错误消失。

验证（本机安装到 `%LOCALAPPDATA%\Programs\UncleNovel` 后）：

- 安装目录 `logs\log-error.log` 为 **0 字节**（无字体加载失败记录）；
- `conf\font.css` 内容为 `.root{-fx-font-family: 'Microsoft YaHei';}`（界面字体为微软雅黑；对应 CHG-07 调优配置生效后的表现）；
- 快捷方式属性核对：`TargetPath = ...\UncleNovel\Uncle小说.exe`、`WorkingDirectory = ...\UncleNovel`、`IconLocation = ...\UncleNovel\favicon.ico,0`；
- 安装后 `conf\conf.json` 的 `download.folder` = `...\UncleNovel\downloads`，证明数据目录 = 安装目录。

#### 3.5.3 风险与回退

- 风险：若用户把目录搬到含中文的路径，字体会回退系统字体并重新出现错误日志（**功能不受影响**，只是内置字体不生效）；若快捷方式被重建且未设置起始位置，数据目录会漂移（表现为“设置丢失”）。
- 回退：无需回退文件；移动到任意路径后按 README §4.2 重建快捷方式并设置起始位置即可。
